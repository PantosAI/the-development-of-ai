发展史：从早期 AI 到 LLM Agent

七十年里，「感知—规划—行动—反思」这个闭环的每一支箭，是在不同年代被逐一接通的。

1.1 什么是 Agent？一个跨越 70 年的定义

Agent 的经典定义早于 LLM 几十年：一个能感知环境、自主决策、采取行动、并根据结果再次决策的系统。Wooldridge 与 Jennings 在 1995 年《Intelligent Agents: Theory and Practice》中将其形式化索引。理解这段历史的关键线索是「循环的哪一支箭在何时被真正接通」：1971 年的 Shakey 机器人就已跑通机械版闭环；真正难的是用自然语言理解、通用推理和开放环境把这个循环做通用。

1.2 早期：SHRDLU、专家系统、STRIPS 与 Shakey

  • 1966 年，ELIZA（Weizenbaum，MIT）：用模式匹配进行对话，常被视为最早的软件 Agent 雏形之一。
  • 1965 年起，Dendral：第一个专家系统之一，做化学分析；1976 年，MYCIN（斯坦福）：约 600 条规则诊断细菌感染并推荐抗生素，是规则式专家系统的标杆。
  • 1970–1972 年，SHRDLU（Terry Winograd，MIT）：在「积木世界」中理解英语指令、移动物体、回答关于自身过去行为的问题，并能发起澄清对话；专著《Understanding Natural Language》1972 年由 Academic Press 出版。它的意义在于语言、记忆与行动首次在同一系统中协同，而非某一单项技术。
  • 1971 年，STRIPS 规划器（SRI International，技术报告 TN-43R）与 Shakey 机器人：把目标分解为有序动作序列，机器人感知房间、规划路径、推动物体——第一台端到端的「感知—规划—行动」机器人。
  • 1986 年，包容式架构 Subsumption（Rodney Brooks）：拒绝中央世界模型，主张行为优先、反应式分层；同年 Marvin Minsky《The Society of Mind》提出「心智由大量本身不智能的小 Agent 组成」，是子 Agent / 编排思想的早期表述。
  • 1987 年 BDI 理论（Michael Bratman《Intention, Plans, and Practical Reason》）区分信念（Belief）、欲望（Desire）、意图（Intention）；1995 年 Rao & Georgeff《BDI Agents: From Theory to Practice》（ICMAS）将其变为理性 Agent 的标准理论框架，至今仍是理解「意图承诺与重规划」的概念源头。
教学要点：专家系统的瓶颈不是规则不够多，而是知识获取瓶颈——每个新领域都要人工编码规则，且无法处理开放世界的不确定性。这正是 MCP 在 2024 年要解决的同一类问题在新形态下的重现：N×M 的集成矩阵。

1.3 强化学习 Agent：从棋盘到通用决策

  • 1959 年 Samuel 跳棋程序；1980 年代时序差分学习；1989 年 Watkins 在博士论文中提出 Q-learning。
  • 1992 年，TD-Gammon（Gerald Tesauro，IBM）：第一个达到世界级水平的复杂博弈 RL 系统。
  • 2013 年 12 月，DQN（Mnih 等，DeepMind，arXiv:1312.5602）：仅用屏幕像素和分数学会玩 7 个 Atari 游戏；2015 年 2 月《Nature》版扩展到 49 个游戏，加入经验回放与目标网络，多数游戏达到或超过人类水平。
  • 2016 年 3 月，AlphaGo 4–1 战胜李世石：蒙特卡洛树搜索 + 深度策略 / 价值网络；2017 年 AlphaGo Zero 完全自博弈、零人类棋谱；2018 年 AlphaZero 同一算法通吃围棋、国际象棋、日本将棋；2019 年 MuZero 不被告知规则也能学会规划模型；2019 年 AlphaStar 在星际争霸 II 达到宗师级——多智能体、部分可观测、实时决策。
  • 2017 年 PPO（OpenAI）成为默认策略梯度算法；2022 年 RLHF 让 ChatGPT「好用」，RL 从游戏走向语言模型对齐；2024–2026 年 GRPO 等 RL 方法成为推理模型与 agentic RL（Search-R1、Kimi-Researcher 等）post-training 的核心。
承前启后：RL Agent 的遗产不是某个算法，而是环境—奖励—探索的思维：现代 LLM Agent 的评估（benchmark 即环境）、RL 训练（用工具轨迹做奖励）与「从失败中反思」（Reflexion 的语言版强化学习）都直接继承了它。

  • 2023-03-30，AutoGPT（Toran Bruce Richards / Significant Gravitas）：给 GPT-4 一个目标，自动分解任务、联网搜索、读写文件、循环直至完成；三周内超 7 万 GitHub star，一度成为 GitHub 史上增长最快的项目之一。

核心架构：循环、推理、工具、记忆、编排与评估

今天任何一个框架的内核，拆开都是同一个循环；差别在 harness、记忆与评估怎么做。

2.1 标准 Agent 循环：感知—规划—行动—反思

目标 / 指令用户任务与约束进入系统
→
感知 Perceive读取环境状态、上下文与记忆
→
规划 / 推理 Plan分解任务、选择下一步动作
→
行动 Act调用工具 / 代码 / 浏览器
反思 Reflect评估结果、更新记忆与计划，决定继续或停止
←
观测 Observe工具返回、环境新状态、报错信息
→
完成 / 交付满足停止条件后输出结果与轨迹
图 1 · Canonical Agent Loop。反思不通过则回到感知，进入下一轮；护栏（步数、预算、超时、审批点）由 harness 强制执行。

Harness（支架）是循环的代码实现：它持有状态、管理上下文窗口、解析工具调用、执行工具、处理错误与重试、强制步数 / 预算上限、记录轨迹（trace）。2026 年的共识是：模型是引擎，harness 是车——同一模型换 harness，可在 SWE-bench Pro 上从 23% 变到 52%（二手独立测量，见第 5 章）索引。

最小可运行循环（教学用伪代码，任何框架的内核都是它）：

while steps < MAX_STEPS and not done:
    action      = model(messages + tools_schema)   # Thought + Action
    observation = execute(action)                  # 工具 / 代码 / 浏览器
    messages   += [action, observation]            # 轨迹即短期记忆
    done, summary = check(action, observation)     # 评估器 / 停止条件
停止条件与护栏必须写在 harness 里，不能只靠模型自觉：最大步数、最大 token / 费用、超时、重复动作检测、审批点。这正是 AutoGPT 时代无界循环的教训（§1.5）。

  1. 推理 ≠ 规划。CoT / ToT 解决「想清楚」，ReAct / plan-and-execute 解决「在环境中推进并纠错」。生产 Agent 两者都要，且后者更决定成败。
  2. 验证器（verifier）比推理链更重要。能用测试、类型检查、数据库状态、计算器复核的结果，就不要只用模型自评。Reflexion 的有效性高度依赖外部评估器质量。
  3. 2025–2026 年的转向：从「提示词技巧」转向「训练出来的 agentic 能力」——深度研究 Agent（o3 版）明确用「端到端 RL 训练于困难浏览与推理任务」；Kimi-Researcher（Moonshot，2025-06）用端到端 agentic RL 使 HLE 从 8.6% 升至 26.9%索引，二手。提示工程仍重要，但上限由训练决定。

2.3 工具使用（Tool Use）

(a) 结构化函数调用

JSON Schema 描述函数，模型返回结构化参数。OpenAI 2023-06 普及，现为各家 API 标配。

(b) 代码执行型

如 smolagents CodeAgent：模型直接写 Python 代码调用工具，表达力最强，沙箱要求最高。

(c) 协议化工具

MCP 服务器（见 §3.1）：工具一次实现、到处可用，治理与审计走网关。

  • 工具设计原则（ACI 论点，SWE-agent 2024）：粒度要匹配模型能力——太细（裸 shell）则模型迷失，太粗则失去控制；返回信息要「可行动」（错误信息应指明如何修复，而非仅报错码）；工具描述本身就是提示词的一部分，写得差等于模型能力打折。
  • 并行调用与批量：多个独立工具可并行；2026 年的计算机操作工具集已支持批量动作（batch）以减少往返。有依赖的调用必须串行。
  • 工具选择失败是常见故障：几十个 MCP 工具全量塞入上下文会稀释注意力、抬高成本；实践是用检索 / 分组 / 按需加载（MCP 的 tools/list + 动态发现、Agent Skills 的渐进披露），只给当前步骤相关的工具。

2.5 检索（Retrieval）与 Agentic RAG

  • 经典 RAG（2020）：查询 → 检索 top-k 文档块 → 拼入提示词 → 生成。适用于知识更新快、私有知识多的场景。
  • Agentic RAG（2024–2026）：检索本身变成 Agent 循环中一个可多次调用、可自我纠错的工具：模型决定搜什么、搜几次、是否换查询、是否深入某源；深度研究 Agent 是其极致形态。失败模式：块切分不当、召回不相关、长上下文「迷失中间」（Lost in the Middle，Liu 等 2023）、引用与原文不符。
  • GraphRAG / 混合检索：向量召回（语义模糊匹配）+ 图 / 关键词召回（关系与精确实体）+ 重排（rerank）组合，是 2025–2026 年企业 RAG 的默认配方；但图谱需要本体维护成本，小规模场景向量 + 良好分块往往已够。

  2. 污染与记忆（Contamination）：模型可能在训练中见过基准任务的解法。SWE-bench Verified 的教训：测试会通过错误补丁、拒绝正确补丁；2026 年 2 月 OpenAI 停报该基准索引。
  3. 任务有效性缺陷：Agentic Benchmark Checklist（ABC）审计 10 个 Agent 基准，发现 7 个有任务有效性缺陷、7 个有结果有效性缺陷、10 个都有报告缺陷；τ-bench 航空任务中什么都不做的 Agent 得 38%；OSWorld 的损坏页面选择器曾使某 Agent 低估 28 分索引，二手综述。
  4. Harness 混淆：榜单分数 = 模型 × harness × 提示词 × 工具。不同厂商用各自 harness 发布数字，跨厂商数字不可直接比较；应看同一 harness 下的消融或官方榜单的同一口径。
  5. 基准 ≠ 生产：基准测固定终态，生产关心成本、延迟、可恢复性、合规与长期稳定性。2025 年一项研究：某 Agent 在 18 个真实 issue 上平均成功率 38%，但 15 个经人工审查的 PR 无一可直接合并索引，二手。因此生产评估必须三层并行：离线基准 + 仿真 / 影子流量 + 在线人工抽检与 LLM-as-judge，并固定 harness 版本做回归。

3.9.1 威胁模型：为什么 Agent 安全 ≠ 聊天机器人安全

3.9.3 防御分层（没有银弹，只有层叠）

  1. 权限最小化与身份：每个 Agent 独立身份、作用域委托凭证（scoped delegation）、按动作授权；绝不共享人类账户；工具白名单。
  2. 沙箱与隔离：代码 / 浏览器 / 文件操作一律在隔离沙箱（容器 / 微 VM）中执行；网络出口控制（egress allowlist）；敏感目录只读挂载或不可见。
  3. 审批门（Approval gates）：不可逆 / 高影响动作（支付、删除、发送、发布、改生产）必须 HITL；审批界面必须展示完整动作与参数，而非模型摘要。
  4. 输入处理：把工具返回、网页、文件、记忆、他 Agent 消息一律视为数据而非指令；结构化分隔（角色 / 通道隔离）、对高风险工具结果做净化与来源标注；注意「模型级防御不是安全边界」——分类器护栏均有已发表绕过。
  5. 信息流控制：实验性方向——CaMeL、Fides、SAMOS 等用能力（capability）与信息流标签约束数据跨边界流动；生产上先用「工具代理（broker）+ 策略」近似。
  6. 可观测性与熔断：全轨迹记录、异常动作告警、每任务超时 / 预算熔断、一键 kill switch、事后审计日志不可篡改。
  7. 对抗评估：把 AgentDojo / AgentVigil 式红队纳入 CI；把 Agent 视为「已被攻陷」来设计测试。

4.2 关键设计决策与失败模式

决策清单（每个决策都要有评估证据支撑）

  1. Agent vs 工作流 vs 单次调用：任务是否需要多步、环境反馈、错误恢复？不需要就不要用 Agent——单次调用 + 确定性代码更便宜、更可靠。
  2. 自主度（Autonomy）梯度：建议 → 草稿 → 需批准执行 → 自主执行（限作用域）。按动作风险分级，而非按 Agent 一刀切。
  3. 上下文策略：摘要 / 压缩、子 Agent 隔离上下文、按需加载技能、工具结果截断与结构化。1M 上下文不是「全塞进去」的许可证——「迷失中间」与成本随长度增长。
  4. 工具粒度与数量：10 个好工具 > 100 个平庸工具；工具描述即提示词。
  5. 状态建模：显式状态机 / 图（LangGraph）vs 隐式对话历史（简单 SDK）。长时、多分支、需审计的任务选前者。
  6. 失败恢复：幂等工具设计、检查点续跑、死信队列、人工接管路径。

4.3 可观测性 / 追踪与评估运营

(1) 离线评估基准 + 自建任务集，CI 门禁
(2) 在线评估生产流量采样，LLM-as-judge + 启发式检查
(3) 人工评估标注队列、抽检、红队
图 6 · 三层评估模型，三层缺一不可。轨迹（Trace）的数据模型：一次用户请求 → 一棵 span 树（LLM 调用、工具调用、子 Agent、检索步骤），每 span 带输入 / 输出、token、成本、延迟、评分。
  • 工具对比（2026-10 核查）：LangSmith（LangChain 出品，追踪 + 评估 + 告警，Agent Server 运行时，自托管为企业版）；Langfuse（开源 MIT，核心功能可自托管，Postgres + ClickHouse + Redis + S3）；Arize Phoenix（开源，追踪 + 评估）；Braintrust；Datadog Agent Observability（与 APM / 安全工具同处）；Trigger.dev（执行可观测性：尝试、重试、等待、HITL 状态）。
  • 选型要点：「LLM 调用可观测」与「运行可观测」是两回事——前者解释坏答案，后者解释「好答案之后运行为何死了」；两者都要。
  • 成本 / 延迟权衡（量化直觉）：① 推理预算调高 → 质量升、延迟与成本同升，语音场景必须调低或双轨；② 长上下文 ≠ 好效果，缓存命中率（prompt caching）是 2026 年成本优化的第一杠杆；③ 模型路由：80% 的步骤用小模型、20% 的关键步骤用大模型，是常见成本结构；④ 并行子 Agent 省墙钟时间、花更多 token，批量工具调用省往返；⑤ 全量追踪成本高，生产用采样 + 错误全采 + 关键用户全采。

4.4 学习路径（4 阶段，4–8 周，每周数小时）

路径原则：先手写循环理解原理，再用框架；先单 Agent 跑通评估，再碰多 Agent；每阶段产出一个可运行、可评估的 Agent，而不是只看视频。
