先说清楚：你已经有 Muse，为什么还要「自己的 Agent」

你现在用 Muse 很顺手——它有独立云电脑、能在授权范围内主动发现任务、能定时执行、还能当独立救援通道。这些都不用推翻。「搭建属于自己的 Agent」不是换掉主力，而是补上三件主力产品给不了你的事：

  • 可替换性。起点文件的判断是：商业服务优先体验，但关键依赖要保留退出权。Muse 是主力，OpenClaw 是它的自建冷备——主力涨价、降级或不可用时，你能低成本切换，而不是临时从零重建。
  • 资产归你。真正值得长期建设的是自己的数据、知识、执行工具和清晰的架构，而不是任何一个产品的生态。记忆、规范、Skills 如果只活在某个产品里，换产品就等于重来。
  • 理解力。起点文件的学习路线说，学 Agent 要走系统路线：能判断、能架构、能取舍、能验收。亲手搭一遍，是把这条路线落到实处最快的方式——搭的过程本身就是学习。

所以本页的目标不是「再装一个软件」，而是：以 Muse 为主力参照，搭出一套你自己掌控的 Agent 系统——说明书、规范、工具、记忆、技能、冷备，一件不少，且每一件都能搬走。

你要搭的到底是什么：模型是引擎，系统才是整辆车

起点文件第一节的核心判断：Agent 不是某一个分支，而是多个分支的集成——模型与推理来自人工智能，代码与实现来自软件工程，协同与状态来自分布式系统，可靠性与成本来自系统与运维，记忆来自数据库与知识工程，指挥与决策来自人机交互。就像汽车不是机械工程的一个分支：发动机、底盘、电子、材料拼在一起才是一辆车。

落到搭建上，这意味着你不需要训练模型，也不需要先学会写一堆代码。模型是现成的引擎，你要组装的是整辆车：

车的部件Agent 的对应物本页对应步骤
引擎大模型（云端订阅、API 或本地推理）第二步：经网关接入，不直连绑死
驾驶舱与传动harness：为模型提供工具、上下文与执行环境的框架第二步：选一个主力 harness
使用说明书Agent 说明书：职责、边界、授权规则第一步
交通规则AGENTS.md：全局工作规范第三步

检验标准（沿用起点文件）：每搭一个部件，都问一句——「它让我能做出什么以前做不出的决策？」答不上来，这个部件先别搭。

总体架构：六层，一张图看懂

整套系统的分工原则只有一条：人保留决策权，AI 承担操作成本。往下每一层都可替换，唯独最上面的「你」和最下面的「你的资产」不动。

动手前准备清单：先定两件事，再按路线备齐

这一节是留着「以后有空动手」时照单核对用的，不催进度。先说一句让你放心的：按起点文件里你的配置，你其实已经有大半家当了——MacBook、Windows、NAS、VPS、Tailscale 私网都在。所以真要新准备的东西不多，主要是先想清楚两件事，再按选定的路线补齐几样账号侧的东西。

先定两件事（不用准备实物，想清楚就行）

  1. 它要负责的第一件事是什么。越具体越好，比如「每天早上查一遍服务器状态，有异常先发我确认再处理」，而不是「帮我管一切」。第一件事跑通了，再加第二件——这也正是第一步写说明书时要落纸的那件事。
  2. 走哪条路线。A：在 Muse 里配好就用，今天就能开始；B：在 VPS 上跑一个现成的自托管 Agent（如 OpenClaw），24 小时在线，用 WhatsApp 或 Telegram 跟它说话；C：从代码写一个完全定制的。A 最快，B 最像「自己的」，C 最自由也最花时间。三条路线要准备的东西见下表，对照着备，不用三份都备。
路线是什么要准备的东西时间（估计）
A · 配好就用在 Muse 里把说明书、规范、记忆配好，直接用基本不用准备实物。给出三样即可：任务（第一件事）、成功标准（做到什么样算完成）、禁区（什么事必须先问你、什么事绝对不许做）对话内当天可开始
B · VPS 自托管在 VPS 上跑现成 Agent（如 OpenClaw），24 小时在线，经 WhatsApp 或 Telegram 联系① 确认那台 VPS 还在，系统与配置够用（一般 Ubuntu、2GB 以上内存，4GB 更稳）；② 一个模型 API 密钥（Anthropic、OpenAI 或 OpenRouter 这类，按量计费、要绑支付方式）；③ 定用哪个消息应用联系它：Telegram 要建一个 Bot 拿 token，WhatsApp 要用手机扫码配对。域名不是必需的，有的话访问更方便配合顺畅的话，约一个下午出第一个可用版
C · 从代码写起自己写代码，做一个完全定制的 Agent在共同材料之外再加：一个代码仓库，和一份具体需求——哪些功能必须有、要接哪些服务，写明后分几天迭代做按天迭代，视需求多少而定

表中时间均为估计，不是承诺：实际快慢取决于账号开通、网络与验收时发现的问题。

不管走哪条，都要准备的材料

  • 你的知识和规矩现在放在哪。Notes、Agent-Memory、以前写过的 AGENTS.md 或 Skills——有现成的直接拿来用（对应第五步、第三步），比重新写快得多；没有现成的，就从本页模板起步。
  • 它要碰的账号与服务清单。邮箱、日历、服务器、NAS，逐项列出，并标明碰到哪一级要你授权——这份清单就是第一步说明书里授权分级的填写依据。
  • 一条救援线。万一它改错了：怎么停、怎么恢复、备份在哪。这条没准备好，就不让它碰真东西——与第八步五条规则里的「保留独立救援通道和可恢复备份」是同一件事。

分工与安全：谁动手，谁点确认

由谁做什么
Muse 可以直接做（在你确认后动手）写配置和代码、装软件、接工具、写指令和 Skills、做验收测试
必须你本人动手注册账号、开 API 额度、付费、扫码绑定（如 WhatsApp 配对），以及在关键步骤上点确认

密码、密钥一律不走聊天：需要时走安全卡片录入，只用、不记。这一条与全页「凭据独立管理」的要求一致——不进知识库、不进任何文档明文。

费用：三笔分开的账

订阅额度、API 按量计费、VPS 租金是三笔分开的账，别混在一起估。具体多少以服务商现价为准；动手前先把每一笔算清楚，你点头再开，不先斩后奏。

第一步 定职责与边界：先写 Agent 说明书

最常见的搭法是先装软件、再想用途，结果是工具装了一堆、没有一件形成闭环。正确的顺序反过来：先用一页纸写清楚这个 Agent 替你干什么、不干什么、什么事必须先问你。这份说明书不是给人看的宣传稿，而是给 Agent 读的工作合同，也是后面每一步的验收依据。

写的时候注意三件事：

  • 职责写成动词清单，不用形容词。「维护个人基础设施：查日志、分析故障、改配置、跑备份检查」是职责；「智能、高效」不是。
  • 边界先写禁止项。起点文件的经验是：防火墙、身份认证、数据删除、远程访问这类高影响变更，永远在「必须授权」一栏，不给任何 Agent 例外。
  • 写明它向谁汇报、用什么形式。结论先行还是过程先行、报告存到哪里、什么情况要立刻打断你——这些不定，Agent 做得越多你越累。
模板 1 ｜ Agent 说明书（存为 agent-spec.md，放在知识库根目录）
# 我的 Agent 说明书

## 它是谁
- 定位：我的个人运维与研究助理。主力是 Muse（云端），
  本地 harness 与 VPS 上的 OpenClaw 为备用路线。
- 原则：它承担操作成本（调查、执行、记录），我保留决策权
  （架构、取舍、授权、验收）。

## 它负责什么（职责清单）
1. 基础设施运维：查日志、分析异常、给出处置方案、经授权后执行。
2. 信息调查：对新项目 / 新工具做初步调查并出报告（见「探索」指令）。
3. 文档沉淀：每次任务后把结论写回 Notes，事实变更同步 Agent-Memory。
4. 定时事务：按我设定的时间跑轻量检查并汇报（备份、磁盘、服务健康）。

## 它不负责什么
- 不做投资、采购等替我花钱的决定；只提供整理好的依据。
- 不替我向任何人发送消息，除非我逐条确认过内容。
- 确定性任务（定时备份、磁盘检查、日志归档）不归它跑，
  归脚本；它只负责解释脚本报告里的异常。

## 授权分级
- 可直接做：只读调查、查日志、读文件、跑无副作用的检查命令。
- 先报告再做：改配置、重启服务、装卸软件——先给方案和影响范围，
  我确认后执行。
- 永远先问：防火墙 / 身份认证 / 远程访问变更、删除数据、
  对外发送、产生费用的操作。

## 汇报约定
- 结论先行，事实与推测分开标注，推测要写明依据。
- 每次任务留一条记录：做了什么、验了什么、还剩什么问题。
- 拿不准就停下来问，不要用猜测补齐缺失信息。

第二步 选 harness 与模型：网关先行，别绑死一家

先把两个词分清（均出自起点文件）：

  • harness：为模型提供工具、上下文与执行环境的框架。模型本身只会「想和说」，是 harness 让它能读文件、跑命令、调工具、记住上下文——同一个模型换上不同 harness，干活能力完全不同。
  • Magpie：起点文件作者跑在 MacBook 上的模型网关。它把「模型供给」与「开发界面」解耦：上游接不同的模型来源，下游哪个 harness 来用都行；同时它还承担统一配置分发（见图 1 第 ④ 层）。

对你来说，这一步的决策很简单，因为主力已经定了：

角色选择理由
主力 harnessMuse（现用，云端独立环境）主动发现任务、定时执行、独立救援通道，用得顺手就不换
本地 harness任选一个本地开发 Agent（如 Claude Code 类工具）处理必须在本机文件与代码仓库里完成的任务
模型接入经网关（如 Magpie 式自建网关）路由，不在每个工具里各填一份密钥换模型、换额度来源时只改网关一处；凭据集中保管
冷备 harnessOpenClaw，装在 VPS 上（第八步）开源自建，主力不可用时顶上，平时不运行

一条口径提醒：起点文件里 Magpie 路由的模型来源是作者本人的订阅与额度安排，作者明确注明「不代表普通订阅天然允许任意第三方调用」。你照这个架构搭时，先看清自己所用服务的官方授权范围、接口与服务条款，再决定网关上游接什么——架构可以学，额度不能假设。

第三步 写全局规范：AGENTS.md

说明书是「这个 Agent 干什么」，AGENTS.md 是「所有 Agent 在我这儿干活的规矩」。起点文件里，Magpie 统一维护 AGENTS.md 等工作指令，分发给接入的各个 harness——这样你换一个 Agent，它一上来就懂你的安全边界、目录约定和验收纪律，不用逐个重教。

一份能用的 AGENTS.md 不求长，求每条都可执行、可检查。下面这份直接脱胎于起点文件的五条运维规则与上下文约定，抄去改成你的版本：

模板 2 ｜ AGENTS.md（全局工作规范，一处维护、多处分发）
# AGENTS.md — 全局工作规范

## 通用纪律
1. 默认先调查，区分事实与推测，再决定是否需要修改。
   报告里事实与推测分开写，推测注明依据。
2. 高影响变更必须授权：防火墙、身份认证、数据删除、
   远程访问、对外发送、产生费用的操作，先给方案，等确认。
3. 保留独立救援通道和可恢复备份：任何远程操作之前，
   先确认「这一步做错了，我还能怎么进去、怎么退回」。
4. 验证实际服务行为，而不只是检查进程是否启动；
   验证不过，按授权回滚，并如实报告。
5. 基础设施变更与文档更新属于同一个任务：
   改完系统，必须同步更新 Notes 与受影响的说明文档。

## 目录与文件约定
- Notes/        详细记录：架构、调查报告、故障记录、操作手册。
- Agent-Memory/ 精简事实：当前状态、我的决策、长期约束。
- 权威写入源只有一处（我的主力电脑）；其他设备只读同步。
- 凭据独立管理：不写进本文件、不写进知识库、不写进任何文档。

## 上下文约定
- 安全规范与当前项目约束始终加载；其余 MCP、Skills、记忆
  按任务需要逐步引入，不无差别塞满上下文。
- 记忆可能过时：具体配置与服务状态以当前文件、日志和
  实际验证为准，不以记忆为准。

## 汇报格式
- 结论先行；做了什么、验了什么、还剩什么问题，三段齐全。
- 资料不足就标注「未知」，不用猜测补齐，不用营销话术。

维护方式：AGENTS.md 只在一处改（起点文件的做法是由 Magpie 统一分发到 Claude Code、Claude Desktop、Codex 等各 harness，具体格式按各家兼容性微调）。云端产品（如 ChatGPT + RDC、Muse）不依赖这套本地分发时，就把同一份内容放进它们的项目指令或说明书里——内容一份，载体可以多个。

第四步 接工具：MCP 三原语

MCP（Model Context Protocol）是连接 AI 与外部工具、数据的标准协议。按官方规范，一个 MCP 服务器对外提供三类东西，先分清再接线，能避免把「读数据」做成「给权限」：

原语是什么由谁决定使用个人搭建的例子
Tools（工具）可执行的函数，能产生动作或副作用模型（调用前应受你的授权分级约束）查服务状态、重启服务、跑备份检查
Resources（资源）只读的结构化数据，以 URI 标识，作为上下文提供应用（宿主决定纳入哪些）把 Agent-Memory 暴露为可检索的资源
Prompts（提示模板）预先写好的交互模板用户（主动选用才触发）「探索新项目」调查模板、故障复盘模板

接工具的纪律，比接什么工具更重要：

  • 第一批只接 3–5 个，且优先只读：文件检索（如起点文件用的 basic-memory MCP 检索 Agent-Memory）、日志读取、服务状态查询。写操作类工具等闭环跑顺了再加。
  • 每个工具逐个验权限：它能碰到哪些目录、能不能写、写错了怎么回滚——对应说明书的授权分级，逐条对上。
  • 工具不是越多越好。每个工具的定义都占上下文（见第七步），接之前问一句：这个任务出现的频率，值不值它常驻？

第五步 建记忆与知识库：两层结构，单一写入源

这是整套系统里最值得长期投资的一步。起点文件的判断很直接：知识库比某个 Agent 更值得长期投资——聊天历史不该成为唯一的运维文档，关键事实要保存在自己掌控的文件里。同时要分清两种记忆：

  • 长期记忆：多年积累的背景——你的学习、项目、技术偏好、历史决策。它让 Agent 不用每次从零认识你。
  • 热记忆：近期工作上下文——刚讨论的方案、最新进度、还没解决的问题。它让连续任务不断线；换一个 Agent 时，交接成本主要就贵在这里。

落到文件上，就是起点文件的两层结构：

层放什么写法谁来读
Notes详细的架构说明、调查报告、故障记录、设计取舍、操作手册写全、写清来龙去脉，人能直接查阅人和 Agent 都读；出事时先查这里
Agent-Memory精简的当前事实、你的决策、长期约束只写「现在是什么」，一条一个事实，过期就改掉Agent 接手任务时先读这里，快速进入状态

三条维护纪律：① 写入源只有一个，多处都能写，迟早写出两个互相矛盾的「事实」；② 任务结束必回写——调查结论进 Notes、状态变化改 Agent-Memory，这是第八步闭环的一部分，不是可选动作；③ 记忆会过时，所以在 AGENTS.md 里写死：具体配置与服务状态以当前文件、日志和实际验证为准。

第六步 沉淀 Skills：把做过的事变成可复用的流程

Skill 是把「你教过 Agent 一次的做法」固化成文件的机制：一个 Skill 就是一个文件夹，核心是一份 SKILL.md（说明 + 步骤），可以再附参考资料和脚本。起点文件里，个人 Skills 由 Magpie 集中维护、统一分发——换 Agent 不必重配，靠的就是这一层。

Skills 之所以能装很多个而不拖垮上下文，靠的是官方设计的三级渐进披露：

级别加载什么何时加载成本
一级 · 元数据每个 Skill 的 name 与 description启动时，全部常驻极小——所以 description 必须写清「做什么、何时用」
二级 · 正文被选中那个 SKILL.md 的完整步骤任务与 description 匹配时一份手册的量
三级 · 附带资源references、scripts、assets 里的文件正文执行到需要时才读 / 才跑用多少算多少

第一个 Skill 不要凭空设计：挑一件你已经让 Agent 做过两遍以上的事（比如「查一台机器的磁盘与服务状态并出报告」），把当时的指令、步骤、验收点整理成 SKILL.md。下面这份可以直接改名套用：

模板 3 ｜ SKILL.md（一个 Skill 的完整最小形态）
---
name: host-health-check
description: 检查一台主机的磁盘、内存、关键服务状态并生成
  健康报告。用户说「查一下某台机器状态」「健康检查」
  「磁盘满了没」时使用。只做只读检查，不做任何修改。
---

# 主机健康检查

## 适用与边界
- 只读调查：不重启、不删文件、不改配置。
- 发现异常只报告并给出建议，等用户授权后再处置
  （遵循 AGENTS.md 的授权分级）。

## 步骤
1. 确认目标主机与访问方式；连不上时先报告，
   不要反复重试超过 3 次。
2. 采集：磁盘占用（按目录排序前 10）、内存与负载、
   关键服务状态、最近 24 小时日志中的错误条目。
3. 区分事实与推测：数字是事实；根因判断标注为推测
   并写明依据。
4. 输出报告：结论先行（一句话总评），再列异常项、
   建议动作、需要授权的事项。

## 验收
- 报告中的每个数字都来自本次实际命令输出，
  不引用记忆中的旧状态。
- 报告末尾写明：本次未做任何修改。

## 附带资源（按需加载）
- references/thresholds.md：磁盘、负载的告警阈值说明。
- scripts/collect.sh：确定性采集脚本，能用脚本拿的
  数据不让模型逐条敲命令。

注意模板最后一行：Skill 里能固化成脚本的步骤就固化成脚本——这正是下一步和第八步反复出现的原则：确定性部分归脚本，判断部分才归模型。

第七步 上下文工程：统一管理，按需加载

搭到这里，你手里已经有说明书、规范、若干 MCP、一堆记忆和几个 Skills。一个自然的误解是：全塞给 Agent，它就最强。起点文件第六节把话说得很清楚：统一管理，不等于统一塞满上下文。工具定义、指令、检索结果、无关项目资料都占上下文窗口，增加消耗与推理负担；实际开销取决于 harness 的加载机制，不能只凭装了多少判断。

  • 始终保留的最小必要上下文：安全规范、授权分级、当前任务的项目约束——这部分不省。
  • 按需引入的：其余 MCP、Skills、记忆条目，随任务逐步加载（Skills 的三级披露就是为此设计的）。
  • 该扩就扩：复杂问题需要充分证据时，主动扩展上下文，不要为了省 token 牺牲质量——省的是无关内容，不是证据。

范例：把「探索新项目」写成一条可复用的指令

起点文件里有一个现成的上下文工程范例：作者在 GPT 里建了「探索新项目」项目，刷到新开源项目时只输入名字，几秒出一份初步调查报告。这个用法能成立，靠的是指令本身写得好。把它的四条写法抽出来，就是你写任何常驻指令的模板：

  1. 默认直接行动：不先反问一串问题，输入项目名就开始调查。
  2. 判断标准先行：先看对本人（你的项目、你的设备、你的学习路线）的价值，而不是泛泛介绍功能。
  3. 比较要有依据并给出明确推荐：不写「各有优劣」，要写清依据和结论。
  4. 把「技术上能不能跑」和「实际上适不适合」分开说：能装 ≠ 值得装。

再加上同一份指令里的取证要求：优先联网核实并附来源与日期、资料不足标注未知、少用营销化描述、不夸大价值。同样要记住它的边界：指令只能定「怎么查、怎么说」，不能保证每次核实都到位；调查报告是初步调查，不是验收——真正动手前，版本、授权、兼容性仍要重新核实。

模板 4 ｜ 「探索新项目」式调查指令（放进项目指令或做成 Prompt 模板）
# 探索新项目 — 调查指令

收到一个项目名（或链接）后，直接开始调查，不要先反问。

## 调查内容
1. 它是什么、解决什么问题、谁在维护、当前版本与活跃度。
2. 对我的价值：与我现有项目 / 设备 / 学习路线的关系，
   能替掉什么、补上什么；先讲对我的价值，再讲功能清单。
3. 横向比较：与同类主流方案比，依据写清，给出明确推荐。
4. 落地判断，分开两栏写：
   - 技术上能不能跑：我的设备、系统、依赖是否满足；
   - 实际上适不适合：维护成本、与现有架构的冲突、退出成本。

## 取证与表达
- 优先联网核实，关键事实附来源与日期。
- 查不到的标注「未知」，不猜测补齐。
- 不用营销化描述，不夸大价值，不把初步调查写成验收结论。
- 报告存入 Notes 的「探索新项目」目录，一项目一文件。

第八步 上线、冷备与运维闭环

先分工：什么归脚本，什么归 AI

上线前做最后一道分流。起点文件第七节的判断：不是所有自动化都值得使用 AI。能用普通程序稳定完成的确定性任务，优先交给 Shell、Python、系统定时器或监控程序；AI 负责调查与判断，不负责「每天到点做同一件确定的事」。

归脚本（确定性）归 AI（判断性）
定时备份与完整性校验解释异常日志、判断潜在根因
磁盘容量检查、服务健康探测设计迁移方案、评估变更影响
日志归档、到期清理读脚本报告，挑出值得你看的异常
状态汇总与定时推送给出处置建议，列明需要授权的事项

冷备：OpenClaw 上 VPS，平时不运行

按起点文件的备用路线：自建 OpenClaw 作为 Muse 的冷备，跑在公网 VPS 上——目标是完成核心能力验收后采用冷备：平时不必持续运行，需要时再启用。VPS 本来就承担公网入口等职责（见起点文件的架构），把冷备放这里，不用新增机器。

按 OpenClaw 官方安装文档，系统要求为 Node 24（推荐；安装脚本会在缺失时自动处理 Node），两种装法任选：

命令 ｜ OpenClaw 安装（据官方文档，执行前请回官方页核对最新版）
# 方式一：官方安装脚本（macOS / Linux / WSL2，推荐）
curl -fsSL https://openclaw.ai/install.sh | bash

# 方式二：npm 全局安装（自行管理 Node 时）
npm install -g openclaw@latest
openclaw onboard --install-daemon
  • 装完先验收，再谈冷备：用验收清单里「冷备」一节逐项过——能启动、能读到同一份 AGENTS.md 与 Agent-Memory、能完成一个只读调查任务、能干净关闭。验收不过，它就不是备份，只是另一台要维护的机器。
  • 冷备也要定期演练：每月手动启用一次，跑一个真实小任务。冷备的价值在切换那一刻，演练就是为了确认那一刻它真的在。
  • 凭据单独配：冷备的密钥在它自己的环境里配置，不从知识库、不从同步盘复制明文过去。

运维闭环：搭完之后，每天这样转

闭环能转起来，靠的是起点文件那五条不可省略的规则（已写进模板 2 的 AGENTS.md，这里再单独钉一遍）：

  1. 默认先调查，区分事实与推测，再决定是否需要修改。
  2. 高影响变更必须授权：防火墙、身份认证、数据删除、远程访问等，先方案、后执行。
  3. 保留独立救援通道和可恢复备份，避免远程操作时把自己锁在设备之外。
  4. 验证实际服务行为，而不只是检查进程是否启动；必要时按授权回滚。
  5. 基础设施变更与文档更新属于同一个任务：验收后同步更新 Notes、总体架构与受影响的说明，留下供人和其他 Agent 查阅的记录。

这五条比 Agent 的自主性更重要。自主性决定它能跑多快，这五条决定它跑偏时你能不能拉回来。

验收清单：搭完之后逐项过一遍

下面每一条都能当场验证。过不去的，回到对应步骤补，不要留「大概没问题」。

说明书与规范

  • 说明书存在且具体：职责是动词清单；禁止项与授权分级写明，高影响变更无一例外。
  • AGENTS.md 只有一处源头：各 harness 读到的是同一份内容；改规矩只改一处。

模型与工具

  • 换模型演练：在网关处切换一次模型来源，主力任务照常完成，harness 侧零改动。
  • 工具权限逐个对过：每个 MCP 工具的读写范围与说明书的授权分级一一对应；写操作工具都有回滚办法。
  • 第一批工具克制：只读优先，总数个位数；说得出每个工具对应的高频任务。

记忆与知识库

  • 两层分工清楚：Notes 写全、Agent-Memory 写精简事实；随机抽一条事实，能在 Agent-Memory 里 30 秒内找到。
  • 写入源唯一：只有主力设备能写，其余设备是只读副本；同步冲突有明确处理办法。
  • 凭据零明文：在 Notes、Agent-Memory、AGENTS.md 里全文搜索，找不到任何密钥与密码。
  • 换 Agent 交接测试：让一个没参与过的 Agent 只读说明书 + Agent-Memory，复述你的系统现状与约束，关键事实无错误。

Skills 与上下文

  • 第一个 Skill 跑通真实任务：不是演示数据；description 写清了触发条件，不相关任务不会误触发。
  • 最小必要上下文：新开一个任务时，常驻的只有安全规范与当前项目约束；其余按需加载。

冷备与闭环

  • 冷备验收通过：OpenClaw 在 VPS 上能启动、能读同一份规范与记忆、能完成一个只读调查、能干净关闭。
  • 切换演练做过一次：假设 Muse 不可用，用冷备完成一件日常小事，全程计时并记录卡点。
  • 闭环跑过一轮真事：从发现异常到记录回写完整走完，五条规则逐条对照，无一省略。
  • 确定性任务已剥离：备份、磁盘检查、日志归档都在脚本与定时器上，不依赖任何模型在线。
