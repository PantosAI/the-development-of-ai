我的目的是什么

目的不是“学 AI”，更不是“会用 AI 写代码”——写代码已经被 AI 替代了。目的是像学一个专业一样，系统地理解 agent：本科、硕士、博士每一层系统学什么、对应到 agent 的哪个部分，都清清楚楚。

目的的落点是决策。AI 的分析、解决问题能力极强，但没有好的决策提出，就没有价值。学习的终点是能判断、能架构、能取舍、能验收——让 AI 去执行，人来决定方向。

目的的入口是运维：以运维为突破口进入 AI 行业，把理解落到真实项目上。

检验标准：每学一个东西，都问一句——“它让我能做出什么以前做不出的决策？”答不上来，就说明还没学到点上。

Agent 属于计算机专业的哪个部分

Agent 不是某一个分支，而是多个分支的集成。就像汽车不是机械工程的一个分支——发动机、底盘、电子、材料拼在一起才是一辆车。

Agent 的组成部分对应的计算机分支
模型与推理：大模型、规划、工具调用人工智能
代码与系统实现软件工程
多组件协同与状态管理分布式系统、云计算
部署、监控、可靠性、成本系统与运维（MLOps / LLMOps / AIOps）
长期记忆与检索数据库、知识工程
人如何指挥 Agent、如何决策人机交互、认知科学

学 agent 有两条路线：模型路线（让模型更聪明，偏研究）与系统路线（让 agent 可靠落地，偏工程）。你的路线是系统路线，运维就是入口。

理解 agent 的正确方式，是以系统为中心，而不是以模型为中心。模型是引擎，系统才是整辆车。

为什么选运维做突破口

  • 模型层最拥挤，也最容易被 AI 自己替代。一窝蜂去学调模型、提示词，那正是 AI 最擅长的部分，竞争最激烈、贬值最快。
  • 价值在生产环境。Agent 能不能稳定跑、成本多少、出问题怎么办、数据安不安全——这些是运维问题，也是企业愿意付钱的问题。缺的不是会调 API 的人，而是能让 agent 系统可靠落地的人。
  • 运维是决策最密集的地方。选什么模型、配多少预算、何时回滚、什么变更要授权、故障时先恢复还是先查根因——这正好对应核心判断：决策比分析更有价值。
  • 运维闭环就是 agent 闭环。发现异常 → 调查 → 授权 → 执行 → 验收 → 记录（见第七节图 7）。练运维，就是在练 agent 的工作方式。
  • 实践场已经在手里。个人基础设施、Pantosona、clinical-case-vault、ai-news——不用从零找项目。
  • 进阶路径清晰。个人运维 → 项目运维 → AI 系统运维 → Agent 运维，每一步都有明确产出。
阶段内容产出
个人运维自己的电脑、服务器、网络（本文实践部分）稳定的个人运维闭环
项目运维Pantosona、clinical-case-vault、ai-news 的部署与维护能说清楚一个项目怎么跑、怎么回滚
AI 系统运维MLOps / LLMOps：模型部署、提示词版本、评估、可观测性、成本能说清楚一个 AI 系统的成本、故障与回滚

Python 的定位

之前没坚持下去，是定位问题，不是毅力问题：把 Python 当成“要学完的一门课”来学，没有落点；AI 能写 Python 之后，学语法的动力更低。

重新定位：Python 是运维的脚本工具，不是学习目标。确定性任务（定时备份、磁盘检查、健康探测、日志归档）优先交给 Shell、Python、系统定时器——这是第七节的判断。

学法：够写运维脚本的 Python 即可，现学现用。AI 帮写，自己负责读懂、改对、判断合不合适。语法可以查，逻辑必须自己懂。

检验：独立写一个“每天检查磁盘、备份、发报告”的脚本，并让它稳定跑一个月。

AI 写代码之后，人还剩下什么

AI 能做AI 做不到
生成代码、解释日志、给出方案、执行明确指令决定系统应该长什么样（架构）

README 的目标就是这个：从“只会调用 AI 写代码”进化为“能掌控 AI 实现复杂架构的总导演”。总导演不需要亲自操作每一台摄影机，但必须懂行，才能指挥、验收、纠偏。

AI 给你十个方案，选哪个、为什么、代价是什么——这是人的工作，也是最值钱的工作。

实践：我把自己的电脑、服务器和网络，交给 AI 来维护了

前阵子，作者的 MacBook 突然出了远程访问故障：人不在电脑旁边，常用的远控软件又无法正常显示桌面。真正麻烦的并不是故障本身，而是他根本没办法走到那台电脑面前去处理它。

最后，是 Muse 通过命令行重启了远控软件的用户代理，又让显示器进入睡眠后再恢复，才帮他重新拿回桌面的控制权。故障的根因还需要进一步排查，但至少这一次，他不用亲自赶回去救火。

对应所学
  • 本科《操作系统》——进程与服务、用户代理（user agent）进程的启停；《程序设计基础》/ Linux 使用——命令行操作。
  • 硕士《高级操作系统》/ 系统可靠性方向——远程故障诊断与恢复：先恢复服务、根因后查，是典型的故障处置顺序。
  • 博士智能运维（AIOps）研究——让智能体自主完成「发现—重启—验证」的自愈闭环，是博士阶段才涉及的研究课题。

这件事让他更加确信：AI 的价值，已经远远超出了聊天、搜索和写代码。他希望由自己来决定系统应该变成什么样，而不是每天亲自维护系统里的每一个零件。

一、为什么我还在折腾个人基础设施？

他的个人计算环境，早已从一台电脑慢慢长成了一套组合：工位上的 MacBook、寝室里的 Windows 电脑与 NAS、两处局域网，再加上一台公网 VPS（虚拟私人服务器）。这些设备分别承担开发、本地模型推理、应用与媒体服务、存储、远程访问等任务。

对应所学
  • 本科《计算机网络》——局域网（LAN）、公网与服务器的基本概念；《操作系统》——Windows / macOS 等多平台系统的基本使用。
  • 硕士《云计算》——VPS 云服务器的租用与部署、NAS 网络存储系统；《机器学习》应用方向——本地模型推理的部署方式。
  • 博士边缘计算与异构算力调度研究——开发、推理、存储分散在不同设备上协同，属于博士阶段讨论的异构系统课题。本科、硕士只打基础，不做此层设计。

如果放在几年前，他大概不会愿意长期维护这样一套东西。安装软件并不难，真正昂贵的是后续的升级、迁移、配置冲突、网络故障、备份和排障——任何一次故障，都可能把原本属于工作和生活的时间切碎。

对应所学
  • 本科《软件工程》——软件维护的概念：软件成本主要不在写出来，而在后续升级、迁移与排障；《操作系统》——软件安装与配置冲突的来源。
  • 硕士《软件系统运维》/ 可靠性工程方向——变更管理、备份策略与系统化排障方法论，硕士阶段才成体系地讲。

改变他判断的，是 AI Agent（能够调用工具、执行任务的智能体）。他可以把调查、日志分析、命令执行和文档维护交给 AI，自己只负责架构设计、关键决策、授权和验收。

AI 没有消除基础设施的复杂性，而是改变了人承担复杂性的方式。

对应所学
  • 本科《人工智能导论》——智能体（Agent）的基本概念：感知、调用工具、执行任务；《软件工程》——人负责需求、验收的基本分工。
  • 硕士《智能系统设计》——Agent 的工具调用与任务规划；《软件体系结构》——架构设计由人把控、执行细节下放的分层思想。
  • 博士自主智能体与人机协同决策研究——「人保留决策权、AI 承担操作成本」的自主性边界划分，是博士阶段的前沿议题，本科和硕士课程只作介绍。

二、整体架构：按职责拆分，而不是按软件堆砌

他的思路不是把所有服务塞进同一台机器，而是让不同设备根据自身特点承担不同职责：

设备承担的职责
工位 MacBook日常开发、本地 AI 推理、个人知识库，以及 Magpie 的模型与配置分发
寝室 Windows 电脑常驻应用、媒体服务，以及部分模型计算任务
寝室 NAS文件存储与备份
公网 VPS公网服务入口、网络辅助连接、自建 RustDesk 图形远控，以及 OpenClaw 备用 Agent
两台软路由各自提供局域网、私网互联和互联网分流
对应所学
  • 本科《计算机网络》——网络拓扑结构、按节点组网；《系统分析与设计》——模块化与职责分离的初步思想。
  • 硕士《分布式系统》——按职责拆分节点、异构节点协同的架构设计；《云计算》——云端与本地混合部署。
  • 博士复杂系统架构研究——多节点拓扑的选路与自适应优化（如私网「按实际条件选路」）属于研究层面的问题，课程阶段只学其基础原理。

这里的 Tailscale 是各节点之间的逻辑私网，并不是所有流量必须经过的中央服务器；RDC 的远程执行通道，也不必依赖这条私网。

对应所学
  • 本科《计算机网络》——逻辑网络与物理网络的区别、去中心化组网的基本概念：私网是逻辑连接，不是中央服务器转发全部流量。
  • 硕士《高级计算机网络》——覆盖网络（overlay network）与按条件选路（直连 / 中继）的设计。

三、为什么 ChatGPT + RDC 是我的绝对主力？

先把概念说清楚：这里说的 ChatGPT，是网页端或手机 App 的云端环境，而不是 Codex，也不是本地运行的开发 Agent。

RDC（Remote Desktop Commander）为云端 AI 提供访问授权设备的文件和命令行的能力。借助它，他可以从手机上提出需求，让 ChatGPT 阅读文件、分析日志、修改配置、运行测试，再把结果沉淀到自己的知识库里。

对应所学
  • 本科《操作系统》实验——文件系统与目录、命令行读写文件；《软件工程》——运行测试、修改配置的基本操作。
  • 硕士《高级软件工程》——自动化测试与配置管理成体系的做法；《知识管理》方向——把执行结果沉淀为知识库，而非留在聊天里。

但真正让他选定这个组合的，不只是它能执行命令，而是——多年积累的个人记忆，终于有了实际执行能力。

长期记忆与热记忆

他从 2023 年开始使用 ChatGPT，多年交流积累了大量关于他的学习、科研、项目、技术偏好和历史决策的记忆，这是长期记忆。与此同时，他习惯在 ChatGPT 中讨论刚产生的想法、最新开发进度、架构取舍以及尚未解决的问题，这些近期工作上下文，他称之为「热记忆」。

举个例子：他刚讨论完一个服务的迁移方案，又决定修改网络拓扑，接着就能从手机发出运维指令。对于一直参与讨论的 ChatGPT，这些任务具有连续性；换一个 Agent，他可能得重新交代为什么这样做、哪些方案已经被否决、进度到了哪一步。

相比之下，Codex 等本地开发 Agent 擅长理解代码仓库、测试结果和项目指令；Muse、OpenClaw 也可以逐步建立自己的记忆。但多年个人背景和持续更新的跨项目上下文，并不是安装几个工具就能立即复制的。

对应所学
  • 本科《数据库系统》——数据持久化保存的基本思想；《软件工程》——代码仓库、项目指令文件的作用。
  • 硕士《自然语言处理》/ 大模型应用课程——上下文与记忆的区别：长期记忆（多年背景）与热记忆（近期进度）的分层管理；《信息检索》——跨项目上下文的组织。
  • 博士大模型记忆机制研究——记忆的巩固、过时与遗漏、跨会话持续更新，是博士阶段研究的前沿问题；文中「记忆可能过时、须以当前文件和日志为准」正是这一研究里的核心难题。

当然也要清醒：ChatGPT 并不能完整读取他自 2023 年以来的所有对话，记忆还可能过时或遗漏。具体代码、配置和服务状态，必须以当前文件、日志和实际验证为准。

讨论中的例子：灵感随记，躺在床上完成文章

作者在与 Reeves 的讨论中举了上面这套分工最落地的例子：有灵感时，在手机上打开 GPT，配合豆包输入法直接记录；记录的内容自动经 RDC 整理到电脑上的 Markdown 文件里。本篇文章就是作者早上醒来突然想写，让 GPT 根据最近的记忆，经 RDC 在电脑里写出的 Markdown 初稿。作者补充说，从有想法到文章发布，全程躺在床上，没有摸电脑。

对照正文分析，这个流程能成立靠三点：一是记忆的连续性，ChatGPT 一直参与讨论，不用重新交代背景；二是 RDC 的受控执行通道，手机上的指令能落到电脑文件上；三是沉淀物是自己掌控的 Markdown 和知识库，而不是只留在聊天里。它的边界也和正文一致：初稿是初稿，记忆可能过时或遗漏，发布前仍要以当前文件和实际验证为准。

Muse 如何补足 ChatGPT + RDC 的短板？

ChatGPT + RDC 已经覆盖了他大部分交互式运维需求，但他仍然需要另一种工作模式：

  • 主动发现任务：Muse 可以在已有目标和授权范围内发现值得跟进的问题，不必总等他想起来再发指令。
  • 独立云电脑：轻量脚本、调查、数据处理等任务可以在它自己的云端环境执行，不必占用个人电脑。
  • 定时与预设任务：他可以随时在手机上安排明确的任务和时间，在自己没空时，让 Muse 按计划完成工作。
  • 独立救援通道：此前他常通过 Muse 云电脑 SSH（远程命令行）管理服务器。如今日常服务器管理基本由 ChatGPT + RDC 接替，但独立执行环境仍值得保留。

这并不是说 ChatGPT 产品完全没有自动化或定时任务能力，而是他目前的普通交互式 ChatGPT + RDC 工作流，和 Muse 的主动性、独立云端执行方式恰好互补。

对应所学
  • 本科《计算机网络》——SSH 远程命令行登录；《操作系统》——定时任务（cron / 定时器）的基本概念，对应文中「定时与预设任务」。
  • 硕士《云计算》——独立云电脑 / 云端执行环境、任务调度；《分布式系统》——把轻量任务放到云端异步执行。
  • 博士主动智能体研究——「在目标和授权范围内主动发现任务」对应博士阶段的 Agent 主动性与目标驱动规划研究，本科、硕士一般只学被动响应式系统。

备用路线上，他选择自建 OpenClaw 作为 Muse 的备用：目标是完成核心能力验收后采用冷备，即平时不必持续运行，需要时再启用。Hermes Agent 则不再是他的重点投入方向。

对应所学
  • 本科《操作系统》/《软件工程》——备份与冗余的基本概念：冷备即备用系统平时不运行、需要时再启用。
  • 硕士《系统可靠性工程》——冷备、功能验收后才切换的灾备策略，与后文「保留独立救援通道」是同一套可靠性思想。

四、网络层：让四类网络能力保持独立

个人基础设施很容易把公网入口、虚拟私网、互联网代理和远程控制混在一起。任何一项配置出问题，都可能影响其他能力。他的思路是把它们分开：

网络能力实现方式
公网访问反向代理与必要的身份验证，按需连接公网服务或内网应用
私网互联Tailscale 连接工位、寝室、VPS 和 Muse；软路由提供子网访问。优先直连，无法直连时根据实际条件使用中继
互联网出口两台软路由独立处理分流，不强制让私网流量与普通互联网流量走同一条路径
图形远控日常使用 UU 远程，自建 RustDesk 作为备用；它们与 RDC 的命令行执行能力互补
对应所学
  • 本科《计算机网络》★ 本节是本科核心课的直接对应：子网与路由、VPN 虚拟专用网、代理与反向代理、内网穿透、直连与中继。
  • 硕士《高级计算机网络》——基于 WireGuard 类技术的私网组网（Tailscale）、软路由分流策略；《网络安全》——身份验证、访问控制与最小权限，管理权限与公开访问权限必须分开。
  • 博士零信任网络与新型网络架构研究——「管理面与数据面分离、不暴露高权限接口」是零信任思想的落地，其理论建模属于博士阶段的研究方向。

图中四个模块的纵向排列仅用于阅读，不代表它们互为流量必经路径。Agent 的管理权限也必须与公开应用访问权限分开，不能为了远程管理方便，就暴露高权限管理接口。

对应所学
  • 本科《信息安全基础》——权限分离与最小权限原则的入门概念。
  • 硕士《网络安全》——管理面与业务面分离、高权限接口不直接暴露公网，是硕士阶段安全架构课的重点。本处与上表重复的网络基础不再重标。

五、开发工具与模型算力：按任务选择，而不是绑定某个产品

ChatGPT + RDC 是他的综合交互与运维主力，但软件开发有独立的工具分工：

工具主要用途
Claude Desktop使用 Claude 官方订阅，主力软件开发
Claude Magpie接入 Magpie 网关，备用开发、桌面运维及杂活
ChatGPT 网页端 + RDC轻量开发、脚本、局部修改与验证

最近他还做了一个实验：不依赖本地开发 Agent 的 harness（为模型提供工具、上下文与执行环境的框架），直接通过 ChatGPT 网页端与 RDC 修改代码、操作项目文件并运行测试。

实际体验让他意识到，这种方式的开发潜力并不低，尤其适合边界清晰的轻量开发；已有个人记忆与最新讨论还可以降低任务交接成本。不过，这并不意味着它在大型工程、复杂并行任务或长时间自主执行方面，已经全面超越专业开发 Agent。

对应所学
  • 本科《程序设计》《软件工程》——开发工具链的使用、轻量脚本与局部修改、软件测试的基本流程。
  • 硕士《高级软件工程》——harness（为模型提供工具、上下文与执行环境的框架）的构成；《人工智能应用开发》——用大模型辅助开发的工程方法。
  • 博士基于大模型的自主软件开发研究——大型工程、复杂并行任务、长时间自主执行的成败，是博士阶段「AI for SE」方向正在研究的问题，尚无课程定论。

Magpie：把模型供给与开发界面解耦

Magpie 是运行在 MacBook 上的模型网关，Claude Magpie 则是连接该网关的开发入口，两者并不是同一个软件。

目前 Magpie 路由的云模型来源只有 ChatGPT 订阅额度与 WorkBuddy 免费额度。Claude Desktop 使用独立的 Claude 官方订阅，ChatGPT 网页端或手机 App 也不依赖这个网关。

如果未来 Google 开放适用的 Gemini 第三方 harness 授权，他也会考虑接入 Claude Magpie；具体可行性以官方授权范围、接口及服务条款为准。这里分享的是他的个人配置，不代表普通订阅天然允许任意第三方调用。

此外，MacBook 保留本地模型推理环境，Windows 电脑提供 Embedding 服务（把文本等信息转换为用于语义检索的向量）。轻量 VPS 则更适合承担业务调度和 Agent 自身的运行，不必重复部署大型模型。

对应所学
  • 本科《软件体系结构》初步——解耦与抽象层：Magpie 网关把「模型供给」与「开发界面」分开，正是解耦思想的应用；《计算机网络》——网关与路由的基本概念。
  • 硕士《分布式系统》/ 服务网关设计——API 网关与模型路由、额度管理；《深度学习》——Embedding 向量表示与语义检索；《机器学习系统》（MLOps/LLMOps）——本地推理部署、模型服务化。
  • 博士大模型推理服务优化研究——多模型来源之间的路由选择、成本与质量的权衡、向量表示的理论问题，属于博士阶段的研究课题。

这里的两种 ChatGPT 访问路径不代表两份独立额度；虚线表示按需或条件性接入。独立算力服务依赖宿主设备在线，真正需要无人值守的应用，必须考虑故障回退、资源上限和依赖链。

对应所学
  • 本科《操作系统》——资源上限与进程依赖的基本概念；《软件工程》——服务依赖关系。
  • 硕士《分布式系统》——依赖链与故障传播、故障回退（fallback）设计：宿主离线时独立算力即不可用，是典型的单点依赖问题。

六、知识资产与上下文工程

知识库比某个 Agent 更值得长期投资

他不希望聊天历史成为唯一的运维文档。即使某个 Agent 很了解他，关键事实也应当保存在自己掌控的知识库中：

  • Notes：保存详细的架构、调查报告、故障记录、设计取舍和操作手册。
  • Agent-Memory：保存精简的当前事实、用户决策与长期约束，让接手的 Agent 可以快速找到真正需要的信息。

两者以 MacBook 为权威写入源，记忆库通过受控的版本仓库和云同步提供跨设备查阅，Windows 保留只读副本。凭据则独立管理，不写进知识库或架构图。

对应所学
  • 本科《数据库系统》——数据的结构化保存与查询；《软件工程》——版本控制（Git 类版本仓库）与技术文档写作；《信息安全基础》——凭据不与普通文档混放的安全意识。
  • 硕士《知识工程》——Notes（详细记录）与 Agent-Memory（精简事实）两层知识库的构建；《分布式数据管理》——权威写入源、云同步与只读副本之间的一致性问题。
  • 博士检索增强与长期知识组织研究——让 Agent 跨设备、跨会话准确取回知识，是 RAG 与个人知识基础设施方向的博士级课题。

Magpie 不只是模型网关

如果每换一个 Agent 都要重新配置记忆、工具、工作规范和技能，工具的可替换性就很有限。因此 Magpie 还承担本地 harness 的统一配置分发：

  • MCP（连接 AI 与外部工具、数据的标准协议）：通过 basic-memory MCP 检索 Agent-Memory，并管理其他任务相关的 MCP 工具。
  • 全局工作规范：统一维护 AGENTS.md 等工作指令，包括安全边界、目录约定、执行与验收纪律。
  • 个人 Skills：集中维护可复用的专业知识、操作方法与任务流程。

接入范围包括但不限于 Claude Code、Claude Desktop（含 Claude Magpie）、Codex、DSH、Antigravity。具体分发格式与启用范围按各 harness 的兼容性调整。ChatGPT 云端 + RDC 不依赖这套本地配置机制，可以直接定向读取授权文件。

对应所学
  • 本科《软件工程》——编码规范与项目约定（对应全局工作规范 AGENTS.md）；《计算机网络》——协议是系统间通信约定的初步概念。
  • 硕士《人工智能系统设计》——MCP 作为连接 AI 与外部工具、数据的标准协议；《软件复用》——个人 Skills 把操作方法沉淀为可复用组件，换 Agent 不必重配。
  • 博士智能体互操作与技能学习研究——不同 harness 之间统一分发记忆、工具与技能的可移植性问题，是博士阶段的前沿方向。

讨论中的例子：“探索新项目”的指令如何管住一次调查

作者在讨论中介绍了另一个落地用法：他在 GPT 里建了一个名为“探索新项目”的项目，系统提示词写明要做详细调查。在 B 站或其他地方刷到新的开源项目时，打开这个项目文件夹，输入项目名字，GPT 就会直接详细调查，并分析这个项目对作者各方面的价值、是否值得深入研究，全程只要几秒。以后有空折腾时再打开文件夹，里面就是一堆待探索项目的初步调查报告。截图中该文件夹已有的条目有 Heretic 项目介绍、介绍 Inkling 2 Mini、Mister Download Manager 调查、Snug 项目调查、DSH Go 项目调查，各条目下的摘要在截图中多为截断显示，这里不补全，也不把这些项目当作推荐。

对照正文分析，这份指令的要点有四条：默认直接行动，不先问一串问题；判断标准先看对本人的个人价值，而不是泛泛介绍功能；比较要有依据并给出明确推荐；部署问题要把技术上能不能跑和实际上适不适合分开说。指令里还要求优先联网核实并附来源与日期、资料不足就标注未知、少用营销化描述、不夸大价值——这正是上一节说的“全局工作规范”的具体形态：规范本身不产生事实，只是把“怎么查、怎么说”定下来。但指令不能保证每一次核实都到位，文件夹里的报告也会随版本变化而过期；真正动手之前，仍要重新核实版本、授权与兼容性，调查报告只是初步调查，不是验收。

说明：指令弹窗里被“保存”按钮遮挡的一行、底部被截断的一行和顶部被模糊处理的一行小字未能完整辨认，上面只整理了清晰可读的部分，没有猜补。

统一管理，不等于统一塞满上下文

更多 MCP、更多记忆、更长的全局提示词、更多 Skills，似乎就意味着 Agent 更强。但上下文自身也有成本。

工具定义、指令、检索结果和大量无关项目资料，都可能占用上下文窗口，增加额度消耗与推理负担。实际开销取决于 harness 的加载机制、缓存与模型策略，不能只凭插件数量判断。

Magpie 应当是统一管理和按需分发的控制层，而不是无差别注入上下文的管道。

必要的安全规范和项目约束始终保留；其他 MCP、Skills 和记忆根据任务逐步引入。复杂问题需要充分证据时，应该主动扩展上下文，而不是为了节省 token（模型处理文本的基本单位）牺牲质量。

对应所学
  • 本科《编译原理》——token 一词的来源：文本被切成的最小单位；《操作系统》——缓存（cache）如何影响实际开销；《算法分析》——资源占用与成本的概念。
  • 硕士《自然语言处理》/ 大语言模型课程——上下文窗口、token 计量与推理负担、KV Cache 等模型策略；这也是「不能只凭插件数量判断开销」的课程依据。
  • 博士上下文工程研究——哪些信息该进上下文、何时按需引入、如何在质量与成本间取舍，是博士阶段新兴的研究方向，硕士课程只讲原理不做此层设计。

他最近研究 Pi，以及尝试通过 ChatGPT 网页端或手机 App 配合 RDC 直接开发软件，正是在探索这个问题。

Pi 是精简本地 harness 的实验环境，不默认加载 Magpie 的整套配置。ChatGPT + RDC 则复用云端长期记忆和近期讨论，再定向读取文件和执行命令。后者也并非零上下文开发，仍需考虑云端系统指令、记忆与会话历史。

他的目标不是单纯把 token 压到最低，而是在满足安全、正确性和验收要求的前提下，用尽可能少的必要上下文获得尽可能高的开发质量。

接下来值得对照记录实际上下文与额度消耗、完成时间、测试通过率和返工次数。这还是探索中的方法，不是已经完成的严格对照实验。

对应所学
  • 本科《软件测试》——验收标准与测试通过率的度量；本科实验课——记录数据、做简单对比的基本训练。
  • 硕士《实验设计》/ 系统性能评估——用额度消耗、完成时间、通过率、返工次数等指标做对照记录的方法。
  • 博士《科研方法论》★ 与本段直接对应：区分「探索中的方法」与「严格对照实验」，要求控制变量与可复现性，是博士阶段科研训练的核心，本科、硕士只做初步接触。

七、不是所有自动化都值得使用 AI

他希望 AI 主导运维，但不希望所有操作都依赖大模型。

能够用普通程序稳定完成的任务，例如定时备份、磁盘容量检查、服务健康探测、日志归档和完整性校验，应该优先交给 Shell、Python、系统定时器或监控程序。

这本对应上面这段话里 AI 适合的那一半：日志异常检测、微服务根因定位、网络流量异常检测三个案例，正是“解释异常日志、判断潜在根因”的落地形态；前面的机器学习、深度学习、自然语言处理章节讲的是方法来源。但它不改变正文的判断：AI 做的是调查和判断辅助，高影响变更仍要授权、现场验收，案例里的模型和数据规模也不能直接等同于个人设备的实际情况。

他给自己的运维流程定了几条不可省略的规则：

  1. 默认先调查，区分事实与推测，再决定是否需要修改。
  2. 防火墙、身份认证、数据删除、远程访问等高影响变更必须得到授权。
  3. 保留独立救援通道和可恢复备份，避免远程操作时把自己锁在设备之外。
  4. 验证实际服务行为，而不只是检查进程是否启动；必要时按授权回滚。
  5. 基础设施变更与文档更新必须属于同一个任务。验收后同步更新 Notes、总体架构与受影响的分图，留下供人和其他 Agent 查阅的记录。

这些规则比单纯追求 Agent 的自主性更重要。

对应所学
  • 本科《网络安全基础》——防火墙、身份认证与授权（规则 2）；《操作系统》/《软件工程》——备份与恢复、回滚、进程启动不等于服务正常（规则 3、4）。
  • 硕士《软件可靠性与安全工程》——高影响变更审批、独立救援通道与灾难恢复设计；《DevOps / IT 服务管理》——变更与文档更新属于同一任务（规则 5）、先调查再修改的变更流程。
  • 博士复杂系统韧性研究与科研规范——保留独立通道避免把自己锁在系统之外，是系统韧性问题；「留记录供他人查阅」与博士训练中的可复现、可追溯规范相通。

八、商业服务优先体验，自建方案保留退出权

他不排斥闭源商业服务。只要它好用、价格合理，就可以作为主力，没必要为了追求纯粹自建而牺牲体验。

但对于已经成为关键依赖的产品，他希望提前准备自建的开源备用路线：

一旦主力服务涨价、体验下降或不可用，他应该能以尽可能低的时间、金钱和重配置成本切换，而不是临时从零重建。为此，重要数据、配置、凭据、任务定义与 Skills 应尽量独立管理；备用路线还需要有明确的迁移步骤和功能验收。

商业服务负责提供当前最好的体验，自建备用负责降低未来的退出成本。

对应所学
  • 本科《操作系统》/ 开源软件常识——闭源商业软件与开源自建软件的区别，本科阶段只建立概念。
  • 硕士《云计算》/《信息系统管理》——供应商锁定（vendor lock-in）、迁移与退出成本、总拥有成本评估；为关键依赖提前备好自建路线、数据与配置独立管理，是硕士阶段系统架构课的典型议题。本处没有对应的博士阶段课程内容，故不标博士。

三本书怎么读：按任务走，不必按顺序通读

上面三本书放进对应章节后，合起来是一条从基本功到系统化、再到 AI 方法的路线，但不是必须通读的台阶。遇到具体任务时反向查书，缺什么补什么；读的时候带着正文的五条规则对照：先调查、要授权、留救援通道、验实际行为、变更与文档属于同一个任务。

回头看，这套基础设施的价值并不在于堆了多少软件，而在于几个原则：

  • 让 AI 承担操作成本，人保留决策权。
  • 把长期记忆与个人知识视为基础设施。
  • 统一管理工具和知识，按需加载上下文。
  • 确定性任务优先使用普通程序。
  • 享受商业服务，同时保留低成本退出的能力。

真正值得长期建设的是自己的数据、知识、执行工具和清晰的架构，而不是任何一个产品的生态。

他希望自己负责决定系统应该变成什么样，而不是每天亲自维护系统里的每一个零件。

对应所学
  • 本科《软件工程》总论——确定性任务优先用普通程序、工具为目标服务的基本原则。
  • 硕士《软件体系结构》——把数据、知识与清晰架构视为长期资产、保持组件可替换的架构原则。
  • 博士博士阶段的独立研究者思维——自己决定系统（研究问题）应该变成什么样，而不是陷在每个零件的维护里；这与博士训练强调的独立提出问题、把握方向相通。
