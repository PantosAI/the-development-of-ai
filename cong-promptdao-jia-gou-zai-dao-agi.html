Prompt→ Skill→ Agent→ Architecture→ AGI ?

从 Prompt 到架构，
再到 AGI 与人

每一层都没有取代上一层，而是把它包了进去—— prompt 没死，藏进了 skill；skill 没死，藏进了 agent；agent 也不会死，会藏进 architecture 里。 价值永远往上一层跑。架构解决的是可靠性，它之后并不自动通向 AGI； 系统越自主，人越要往定目标、做判断、担责任的那一层走。而当 agent 成为日常， token 消耗了多少，说明的只是投入，不是事情推进了多少。

问 一最近是 prompt、skill、agent，接下来是 architecture 吗？
问 二接下来还需要人吗？再往下就是 AGI 了吗？
问 三天天用 personal agent，哪天不消耗点 token，为什么会觉得像有件事没做？
01

四层台阶：一层包住一层

点开每一层看它解决了什么、又留下了什么问题——正是那个没解决的问题，把行业推向了上一层。 最上面那层画成虚线，是因为它不在同一摞里——它属于另一条轴。

▲ 上层包住下层 · 底座是模型本身

套娃结构：打开架构，里面层层都在

ARCHITECTURE — 编排 · 记忆 · 协议 · 评估 · 运维
AGENT — 规划、循环、调用工具、看反馈调整
SKILL — 打包好的能力：流程 + 工具 + 规范
PROMPT — 仍然是每一次调用的最终形态

最里面还是那句被精心写下的话。层级上升不是淘汰，而是把下层的"手艺"变成上层的"零件"。

02

Architecture 不是新玩具，是一组系统问题

前三层问的都是"怎么让模型做事"，架构层问的是另一类问题：一群会自己做事的程序，怎么在生产环境里可靠地跑起来。 它拆开是五个子系统，每一个缺位，都有对应的翻车方式。

编排 ORCHESTRATION

任务怎么拆、谁调度谁、并行还是串行、一个 agent 卡住了整个流程怎么办。这是把"一个聪明的个体"变成"一个能交付的流程"的那一层。

缺了它：agent 互相等死、任务悬空、失败无人接手，只能靠人盯着日志手动重启。

记忆与知识 MEMORY

长期记忆放哪、怎么写入和更新、多个 agent 之间怎么共享，记错了怎么发现、怎么纠正。记忆不是存得越多越好，而是要能过期、能溯源、能删除。

缺了它：每次对话从零开始；或者更糟——把一次错误结论当成事实，永久地、自信地用下去。

协议 PROTOCOLS

MCP 让 agent 以统一方式接工具和数据，A2A 让 agent 之间能互相发现、对话、交活。有点像当年的 HTTP 之于网站：单点能力再强，没有互联标准也长不成生态。

缺了它：每接一个工具写一遍胶水代码，每换一个模型重构一遍，系统被供应商和接口焊死。

评估与可观测 EVAL & OBSERVABILITY

跑偏了怎么发现、效果怎么量、每一步的决策能不能回放。没这层，系统再惊艳也不敢上线——因为你不知道它今天和昨天有什么不同。

缺了它：改一处 prompt，三处悄悄退化；用户投诉时，你连它当时"想"了什么都查不到。

运维与成本 OPS & COST

部署、灰度、回滚、权限边界、速率限制、故障演练，还有一本明账：每个任务烧多少 token、值不值。 agent 是会自己做决定的程序，失控的循环能在一夜之间烧掉一个月的预算——这正是传统运维的基本功直接迁移过来的地方： 监控、告警、熔断、限流、预案，一个都不能少，只是监控对象从服务器变成了"会思考的进程"。

缺了它：demo 惊艳，上线三天：账单爆炸、权限越界、故障无法回滚。

03

瓶颈已经变了：从"够不够聪明"到"够不够可靠"

为什么架构层偏偏现在浮上来？因为有个乘法躲不过去：一个任务要连续做对很多步， 整体成功率 = 每步成功率的连乘。单步看着很高的数字，连乘之后会塌得很快。自己拖一拖：

裸跑到底
—
每步可重试一次
—

裸跑成功率 = pn；每步失败后重试一次，等效单步成功率为 1 − (1 − p)²，再连乘。 重试、校验、回滚、兜底——这些不是模型的聪明，是架构的活儿。

这就是那句判断的算术版：一个 agent 连续跑一百次不出错，比它某一次跑得多漂亮更值钱。 演示看的是上限，生产看的是下限。谁在为下限负责，谁就站在架构层——这也是运维出身的人做 Agent 的天然优势： 别人还在调 prompt，你已经在想它挂了怎么办。

04

架构的下一步，不是自动等于 AGI

这是两个不同维度的问题，别混成一条线：架构是工程问题——怎么把系统组织得可靠； AGI 是能力问题——智能有多通用。架构越好，系统越能干，但"通用智能"那道门槛是不是就此跨过去，没人能打包票。

能力高 · 组织低

惊艳但不敢用

演示时惊为天人，长任务就漂移、出错没人兜底。今天大多数"哇塞"型 agent 住在这里。

能力低 · 组织高

可靠但天花板低

流程稳、账算得清，但任务稍复杂就做不了。传统自动化和 RPA 是这一格的居民。

两轴都高

目标格

行业真金白银正在往这里流：不是等一个更强的模型，而是把现有能力组织成可交付的系统。

关于 AGI

它在纵轴的远端

AGI 是能力轴尽头的问题，和横轴的工程进度互相促进、但不互相替代。发动机再强，整车工程也不会消失。

AGI 何时到来：三种声音，尚无共识

近在眼前派

认为靠规模、数据和现有路线的迭代，通用能力会在可预见的几年内涌现，架构工程就是在为它铺跑道。

还差突破派

认为当前路线缺了某些根本性的东西——比如真正的持续学习、因果理解或样本效率——补上之前，能力轴会先进入平台期。

定义存疑派

认为"通用智能"本身没有公认的验收标准，争论一部分是词义之争；与其等定义，不如盯住一个个具体能力被逐个攻克的事实。

诚实的说法是不知道——而且不用等这个答案再行动。无论哪派是对的，横轴（架构与可靠性）的工作都不会白做： AGI 若来，需要架构来约束和部署它；AGI 若不来，现有系统离"可靠"还差得远，活儿只多不少。

05

还需要人吗：需要，但人往上移

历史上的自动化每次都走同一条曲线：机器接手执行层，人走到定义问题、做判断、担责任的那一层。 岗位的名字会变，"被全自动掉"的从来是任务，不是责任。

正被机器接手的（执行层）留在人身上的（判断层）
按既定流程执行多步任务、调用工具、整理信息定目标：什么叫"做好"、什么值得做
生成初稿、写样板代码、做常规巡检和报表断模糊：需求不清、两边都有道理时拍板
在明确规则内做分类、匹配、调度担责任：出了事谁负责、谁签字、谁叫停
7×24 盯着指标，异常时先自愈或先告警守系统：设计它、评估它、它失控时修得了、停得下
定

目标是人定的

机器可以优化一个被给定的目标，但不会替你选目标。"把客服成本降三成"还是"把满意度做到第一"，这是价值排序，不是计算题。

断

模糊是人断的

真实世界的需求永远写不全：两条规则冲突、客户话里有话、数据在撒谎。这些没有标准答案的时刻，需要有人权衡并承担判断的后果。

守

系统是人守的

架构越复杂，越需要有人能看懂它、评估它、出问题能修、能拍板。系统越自主，这双"能踩刹车的手"反而越值钱。

所以结论并不悲观：agent 是干活的，architecture 是干活的组织方式，人是决定"干什么、干成什么样、出了事算谁的"的那一层。 这层不是执行问题，是责任问题——自动化不掉。

06

当 Agent 成为日常：Token 是油，不是目的地

天天用 personal agent 之后，哪天没消耗点 token，心里就像有件事没做完。 这个感觉一半是错觉，一半是信号，值得认真拆一拆。

这种感觉是从哪来的

Agent 把"想做"和"做到"之间的摩擦几乎清零了：以前一件事要自己查、自己写、自己跑流程， 现在开口就有回音、有产出。久而久之，大脑会给"今天干没干活"找一个最容易看见的刻度， 而 token 恰好是整条链路里唯一实时跳动、人人看得懂的数字：对话轮数、消耗量、连续使用天数，全在明面上。 于是"仪表在动"被悄悄等同于"事情在推进"——这和看步数判断锻炼、看提交记录判断写代码是同一种心理： 不是人在骗自己，是可测量的东西天然会挤走不可测量的东西，成为默认的记分牌。

错位在哪：投入被当成了产出

Token 是投入，不是产出。它只证明 agent 被调用过，不证明任何一件事往前挪了。 空转同样烧 token：反复改一版没人看的文案、让 agent 做本来不需要做的事、为了"用一下"而找事给它做—— 仪表一样热闹，事情原地不动。下面是同样平常的两天，换一把尺子量，结论正好相反：

某一天 · 甲

TOKEN 消耗：很高 · 对话几十轮

让 agent 改了五版文案、查了一圈资料、生成了三份草稿。每一份的结局都是"先放着"——没有一份发出去，也没有一个决定做下来。

这个刻度说

某一天 · 乙

TOKEN 消耗：很低 · 只聊了十分钟

只问了一件事：一个卡了三天的选择题，把利弊摆开，当场拍了板。之后一整天的工作，都顺着这个决定往下走。

这个刻度说

甲日并不少见，甚至很典型：忙的是 agent，停住的是事情。 乙日提醒的是另一件事：agent 最大的价值常常不在"生成了多少"，而在某一次调用帮你卸掉了一个卡点—— 这种价值和 token 消耗几乎不相关。用油量评价一趟行程，只能得出"开得多"，得不出"到了没"。

但这感觉也不全是错觉

先别急着否定它。每天惦记着用一下，说明工具真的融进了工作流，而不是躺在收藏夹里吃灰—— 这是任何新习惯最难的一关，已经过了。而且日常使用有实打实的复利：手感（知道什么活适合派给它）、 边界感（知道它在哪类问题上会自信地胡说）、问题意识（遇到事第一反应是"这能不能拆给 agent"）。 这些都是在真实使用里长出来的，读多少文章都替代不了。需要警惕的只有一步：别让习惯反过来指挥人—— 从"我有事，所以用它"，滑到"我要用它，所以找事"。前一句里 agent 是工具，后一句里人成了给仪表打卡的工具。

这其实是你自己的"评估子系统"

架构层缺了评估与可观测，系统就会悄悄退化。个人使用是同一个道理，只是被评估的对象换成了你自己。 管理学里有句老话常被引作古德哈特定律：一个指标一旦变成目标，它就不再是个好指标。 你拿 token 当记分牌，就会不自觉地优化 token——多聊、多生成、多开会话； 你拿"推进"当记分牌，优化的才是事情本身。给系统装什么仪表，系统就往哪儿长；给自己装，同样如此。 所以要换的不是习惯，是仪表。

换个刻度：睡前一分钟，只问三句

  • Q1今天哪件事因为 agent 往前挪了？挪了多少——一个决定、一份成稿、一个卡点被卸掉，都算。
  • Q2今天的消耗里，有多少是空转？重复问、无目的地生成、为用而用——认出来就行，不必自责，认出来下次就少了。
  • Q3如果明天只能用一次 agent，我会把这一次用在哪？这一问逼出来的答案，通常就是明天最该推进的那件事。

最后留一句给"零 token 的日子"：想清楚一个问题、陪人好好吃顿饭、睡个午觉把状态回满—— 这些推进都不经过对话框，仪表上一个数字都不会跳，但它们可能比哪天都重要。 Agent 是杠杆，项目是支点，而日子本身，才是要撬动的那个东西。 哪天没烧 token，先别急着觉得缺了点什么——问一句"今天有事推进了吗"，有，就不缺。

07

站在运维这一侧，往架构走的路

架构层的五块拼图里，运维与成本、可观测、故障处理本来就是运维的基本功——这条路线不是转行，是把已有功夫接到新对象上。

  1. 单机与系统基本功

    进程、内存、磁盘、网络、权限——先能回答"这台机器现在怎么样、为什么"。

  2. 服务与部署

    把程序变成服务：部署、配置、日志、开机自启、坏了能回滚到上一版。

  3. 可观测与故障处理架构层的入场券

    监控、告警、定位、恢复、复盘。这套"发现问题—止损—根因—防复发"的肌肉，正是评估与可观测子系统的原型。

  4. Agent 运行时

    把 agent 当成一种特殊的服务来运维：它的"进程状态"是上下文，它的"故障"是跑偏和幻觉，它的"账单"按 token 计。

  5. 多 Agent 编排与评估

    调度、协议、共享记忆、效果评估——到了这一级，你做的已经是 architecture 本身。

自测六问（先想，再看答案）

Q1

一个 agent 每步成功率 98%，连续跑 50 步，整体成功率大约是多少？这说明了什么？

0.9850 ≈ 36%。单步看很优秀的数字，连乘之后只剩三分之一强——这就是为什么长任务必须靠重试、校验和兜底等架构手段，而不是指望模型"再仔细一点"。在可靠性计算器里拖一下就能验证。

Q2

用一句话说清 Skill 和 Agent 的区别。

Skill 是"能力"，Agent 是"会自己决定何时、按什么顺序使用能力的主体"。技能是被打包的流程和工具；智能体多了规划、循环和根据反馈调整的自主性。

Q3

为什么说协议之于 Agent，有点像 HTTP 之于网站？

HTTP 的价值不在某个网站，而在于任何浏览器能打开任何网站。MCP、A2A 同理：工具和 agent 按同一标准说话，生态才能自由组合，而不是每家各写一套私有接口、彼此焊死。

Q4

一个演示效果惊艳的 agent，为什么通常不能直接上线？

因为演示只证明了"上限存在"，上线需要的是下限有保障：评估（知道它多准）、可观测（出事能查）、兜底（失败有退路）、权限（不能越界）、成本（烧钱有上限）。这五样正是架构层。

Q5

假如 AGI 明天就到来，架构层会消失吗？人的"守系统"角色呢？

都不会。能力再强，也要被部署、被约束、被评估、被审计，出了事要有人叫停和负责——发动机再强，整车工程和交通规则也不会消失。能力轴冲得越高，横轴反而越重要。

Q6

今天 token 消耗是昨天的三倍，能说明今天 agent 用得更好吗？该用什么刻度替代？

不能。token 是投入指标，空转和真推进烧得一样多。用它当记分牌，人就会不自觉地优化消耗本身（古德哈特定律）。替代刻度是"推进"：今天有哪件事因为 agent 往前挪了——决定做下了、成稿交付了、卡点卸掉了，哪怕只挪一小步，也比满格的仪表更算数。

要点回顾

  1. 层级是嵌套，不是替代。prompt → skill → agent → architecture，下层永远在上层里面活着，价值往上跑。
  2. 架构 = 编排 + 记忆 + 协议 + 评估 + 运维。它回答的不是"能不能做"，而是"能不能可靠地、规模化地一直做"。
  3. 可靠性是乘法。单步 99%、连跑 100 步只剩约 37%——瓶颈已从聪明移到可靠。
  4. 架构 ≠ AGI 的下一站。一个是工程轴，一个是能力轴；互相促进，不互相替代，时间表无人能打包票。
  5. 人往上移，不出局。定目标、断模糊、守系统、担责任——这一层自动化不掉。
  6. Token 是油，不是目的地。它量的是投入，不是产出；评估自己用 agent 用得好不好，别看消耗，看推进——你用什么刻度量自己，就会不自觉地优化什么。

可靠性一节的数字按 pn 现场计算；关于 AGI 何时到来，三种立场都只是讨论框架，不是预测。
